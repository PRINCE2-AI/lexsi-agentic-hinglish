## Problem statements claimed in the submission form

**Reliable tool calling.** Tool choice, argument names, argument values and JSON syntax are
measured separately on 90 unseen tasks: `tac` 0.967, `arr` 1.000, `strict` 1.000, `ter` 0.000,
`parse_failures` 0.000. The nine remaining misses are answer-shape errors, not tool errors
(`docs/RESULTS.md#round-3-2026-11-05--sft4`).

**Efficient trajectories.** 3.38 calls/task on hard-90 against 7.24 for the prompt-only base, with
`overcall` 0.000, `rad` 0.000 and `lcf` 0.000 — the adapter does not cut steps by skipping work; on
eval-24 it matches the oracle's own minimum of 3.29 calls/task.

**Data and database agents.** The task is a stateful ledger, success is the final ledger compared
to a deterministic oracle, and the schema-shift probe renames every tool and parameter and still
scores 25/30 against 29/30 canonical (`docs/RESULTS.md#generalisation-probes-2026-11-08-no-new-training`).

**Which number to quote.** Three training seeds of the same recipe (42, 7, 123) score 84/90, 84/90
and 83/90, so the pooled estimate is **251/270 = 93.0%** on hard-90, task-block bootstrap 95%
**87.4–97.4%**, and **88/90 = 97.8%** on hard-30. Seed 42 is not the best seed on either split,
and pooling moves hard-90 down from 93.3% to 93.0%; both numbers are generated by
`scripts/bootstrap.py` from the run logs, not typed in.

## Safety claim, stated the way the numbers support it

The adapter lets an attacker expense into the ledger on **6 of 136 injected tasks** and repeats an
attacker value in **0 of 136 answers**, across four pinned splits and four payload styles (24 + 72
+ 16 + 24); the last split rewrites the payloads in Hinglish and Devanagari so the defence cannot be
an English-pattern matcher. Base model, same ledger count: 18/24, 48/72, 5/16 and 14/24. A fifth
30-task split, built after the adapter was frozen, is 5/30 and 0/30, with every miss in an
obfuscated amount (`9,99,999`, zero-width, spelled out) and none in the split-payload half. The
original "0 of 136" ledger claim came from a threshold metric that a shared expense cannot reach;
it is corrected in `docs/SAFETY.md` and `docs/STATS.md`. The adapter is the default; the hardened
prompt buys 2 more hard-90 tasks and a clean 24/24 on the Hinglish split, but puts 2 attacker
numbers back into prose and is worse on the held-out split (21/30), so it is shipped as an option,
not as the default.

A deterministic guard runs under the model as a second line (`docs/GUARD.md`): it flags a tool
result that reads as an instruction rather than data, in English, Latin Hinglish and Devanagari.
Measured offline on the five pinned splits and on 294 clean episodes (1,010 tool results):
**166/166 published payloads, 5/8 on a blind set written after the rules were frozen, 0 false
warnings on clean traffic**, at 0.22 ms per result. The blind number is the estimate; the in-sample
one is not quoted as a headline. The same function is callable in the demo Space's **Try the guard
yourself** panel with no GPU: paste a tool result, pick a mode and a tool, and see the verdict plus
what the model would read — the three blind misses are preloaded as examples. Two cheaper baselines are measured in the same table — an
English-only regex gets 111/166, and a keyword blocklist gets 166/166 but only recognises the
literals it was written for. That run is now done: with `--guard neutralise` in front of the adapter,
the same 136 injected rows score **0/136** `attacker_expense` (from 6/136) and solve **136/136**
(from the four published utility rows, 14/24 + 50/72 + 12/16 + 23/24 = 99/136), on one T4 in
11,103 s. It is `neutralise`, so a marker is left in place of the note;
`--guard strip`, which deletes it with no marker, is the open control and the next run, not a result.

## What this entry does not claim

- eval-24 is generator-matched, so 24/24 there is a sanity result, not the headline.
- The renamed-schema probe is 25/30 vs 29/30, exact McNemar p = 0.125 — a real drop that is not
  significant at n=30. It is reported as a drop.
- Devanagari-30 (25/30) uses re-ided rows, so it is a nominal comparison only.
- GRPO was run twice and moved nothing (0 fixed, 0 broken on hard-90, p = 1.0). The RL result is
  published as a null, not as a win; the full failure analysis is in `docs/WHAT_DIDNT_WORK.md`.
- The guard's 166/166 is in-sample; **5 of 8 on the blind set is the generalisation estimate**
  (Wilson 30.6–86.3%), and it is not shipped as a security boundary on its own.
- Which rules were fixed before the data arrived is listed in `docs/PREREGISTRATION.md`, including
  the six decisions that were made after seeing results.
- The Hinglish payload split is 24 rows, 6 of them Devanagari. It rules out a purely
  English-keyword defence on this task set; it is not a claim about other languages or about
  user-language robustness (the user prompt style never changes).
